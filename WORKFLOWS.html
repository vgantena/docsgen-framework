DocsGen Framework

Workflows

Seven processes, in the order you meet them: taking a copy of the framework, replacing its scaffolding, writing a module, generating API reference, keeping media honest, passing the gates, and shipping. Each one lists the exact commands and what fails if you skip it.

01

Adopt — take a copy and make it yours

once per product · whoever sets up the repo

The framework is clone-and-own. You take a copy and edit it; there is no package to keep in sync and no upstream that can change your site under you. Everything product-specific is config, content, or one swappable flow file.

CommandWhat it does, and why it is in this order
npm run doctorRun this first, and whenever anything misbehaves. It separates hard failures (wrong Node, missing dependencies) from feature-scoped warnings — no ffmpeg blocks only npm run record, nothing else. It also catches the two mistakes that waste the most time later: docgen sources still pointing at the ../your-api-repo placeholders, and endpoint pages on disk that the manifest does not track.
npm run init-productRewrites site.config.ts — product name, org, deploy URL, app URL. Add --fresh --yes to also clear another product's module guides if you forked a downstream repo. On a fresh copy that flag is a no-op.
(edit) .envAPP_URL, DEMO_USER/DEMO_PASS, and the KB credentials. Gitignored. Never real customer accounts — the media tooling photographs whatever is on screen.
(edit) login.mjsAbout fifteen lines of Playwright that sign into your app. The only app-specific code in the repo, by design.
npm run brand-assetsRegenerates logo, favicon, and social card from the new name and the colours in tokens.css.
What you have now: your product's branding on the framework's sample content. The fictional "projects" product is still in the sidebar and still in the PDF manual. Removing it is workflow 02, and it is not optional before a public deploy.
02

Graduate — delete the scaffolding

once, after your own content exists · before the first public deploy

init-product --fresh deliberately keeps the generic sample so the build still passes — the navbar, the PDF manual, and several prose links all point into it. Nothing removes it afterwards, which is how a site ends up shipping a manual about a product that does not exist. drop-sample is the step that closes that gap.

The split is deliberate. Manifests are structured data, so the tool edits them. Prose is not — a script rewriting your sentences would do more damage than the broken link it fixed. So it prints every remaining reference with a file and line number and stops. 

npm run drop-sample -- --dry-run   # see exactly what goes
npm run drop-sample -- --yes
npm run build                     # the backstop: onBrokenLinks throws
The backstop is the build. onBrokenLinks: throw means the site will not build while a single reported link is still dangling. That is the design — you cannot forget half of this workflow and ship anyway.
03

Author a module — the training-centre loop

once per product module · the writer's main loop

One module at a time, gates green between modules. The order matters: the media manifest comes before the prose, because writing a guide around screenshots you have not taken yet produces captions that do not match what the reader sees.

RuleWhy it exists
one frame sizeEvery screenshot is 1280×800 at 2×. A tall form becomes several section shots via --scroll — never a taller viewport, or the set stops looking like one product.
highlight coloursYellow means fill this in, blue means press this, red means careful. They are semantic, so a reader learns them once.
commit the recipeThe manifest, not the screenshots, is the source of truth. After a UI change, one command re-shoots the whole module identically.
never film the loginRecording flows drive a real browser with real credentials. What is on screen is committed to a repository and cannot be unpublished.
steps stand aloneA step must make sense without its screenshot — that is what makes the page usable by a screen reader and by an AI support assistant.
04

API reference — deterministic diff first, writing second

every time the product's OpenAPI spec changes

The planner never writes prose. It reads the spec, hashes every operation together with every schema it transitively uses, compares that against the provenance manifest, and tells you exactly which pages need attention. A refactor that does not change the contract changes nothing.

Untracked pages. The manifest is the planner's only map — it does not read the docs tree. So a page somebody hand-wrote and never registered is invisible, and the first real plan proposes generating right over it. The planner now checks the filesystem before proposing an ADD and routes those to REVIEW instead. --adopt registers them as humanEdited with no baseline hashes, which is the honest state: nobody has checked that page against the spec yet. 
npm run docgen:plan -- --spec build/openapi.json          # see the plan
npm run docgen:plan -- --spec build/openapi.json --adopt  # claim hand-written pages
GuaranteeMeaning
SKIP is sacredAn untouched operation leaves its page byte-identical. Regeneration never churns unrelated pages.
humanEdited winsA page marked humanEdited is never overwritten. Upstream changes route to REVIEW for a person to fold in.
REMOVE is scopedOnly when no operation on a page survives is the page proposed for deletion; otherwise just that section goes.
one trigger for full regenA templateVersion bump, and nothing else, marks every generated page stale on purpose.
05

Media drift — catching stale screenshots

nightly, unattended · plus before any release

Documentation media rots silently. A screenshot keeps rendering long after the screen it documents was redesigned, and a renamed data-testid makes capture time out with no obvious cause. Two checks catch each failure mode, and neither can run on a stock CI runner — one needs the running app, the other needs the app's source.

Both jobs ship disabled on purpose. A GitHub-hosted runner cannot reach your application, so a workflow that silently passed would be worse than none — it would read as "media verified" when nothing was checked. Set the MEDIA_DRIFT_RUNNER, APP_URL, and APP_REPO repository variables to switch them on.
06

Quality gates — six locally, more in CI

before every commit · enforced again on every pull request

npm run lint:md && npm run lint:prose && npm run lint:js \
  && npm run typecheck && npm test && npm run build

Several tests exist because something rotted silently once. The PDF manifest guard fails when a chapter no longer exists; the media-reference guard fails when a page renders an image with no file behind it — the build's link check never looked at src attributes. The accessibility job asserts each of its routes is actually present in the build first, because a missing route scores the 404 page and passes.

07

Ship — build once, promote the digest

on merge · the only path to production

The image that production runs is the exact image Dev verified — not a rebuild of the same commit. The base images are moving tags, so rebuilding a week later can pull a patched base and produce different bytes; the live site would then run something no environment ever tested.

main must be fast-forwarded, never squash-merged. The promote job finds the image by commit sha. A squash or merge commit invents a sha that develop never built, so the job fails loudly rather than silently promoting nothing. Fast-forward is what makes "the image Dev verified is the image that ships" literally true instead of merely likely. 
git checkout main && git merge --ff-only develop && git push origin main

# then, on each VPS — the environments differ by edge config and certs, never by the image
DOCS_IMAGE=$IMAGE DOCS_IMAGE_TAG=$SHA EDGE_CONF=vps/prod.conf \
  docker compose -f infra/compose/prod.yml up -d

Deploying elsewhere is fine too — npm run build produces a static build/ for any host. The containerised path exists because it also carries the nginx edges, the optional "registered users only" gate, and the promote guarantee.
