DocsGen FrameworkArchitecture

One docs repo, four products out

DocsGen is a reusable help-center framework (Docusaurus + custom tooling) whose single markdown source tree produces four synchronized artifacts: the public docs website, a printable PDF manual, scripted screenshots/videos, and a knowledge-base corpus ready to ground an AI support assistant. Every page is written once, gated by lint/tests, and exported everywhere it is needed — for whichever product adopts the framework.

Repo
docsgen-framework — Docusaurus 3, docs-only mode, custom MDX components, Node ≥ 20.
Philosophy
Deterministic diff first, AI second: nothing regenerates unless a content hash changed, and human-edited pages are protected by provenance flags.
Adopting product plugs in via config
Product name/URLs in site.config.ts, KB vocabulary + API path in docgen.config.json, secrets in .env — the framework itself stays product-free.

Three layers of configuration, deliberately separated: machine tools (installed once per workstation), product identity (committed, per product), and secrets/environment (gitignored, per machine).

Each binary powers one exporter: pandoc+typst → PDF · vale → prose gate · ffmpeg → video pipeline. doctor fails hard only on Node/deps breakage; missing media tools degrade those features with a warning.

2 · Product identity (committed)

site.config.ts
Product name, URLs, navbar, footer, announcement bar. The only file that knows which product this docs site is for. npm run init-product bootstraps a fresh product.
src/css/tokens.css
Colors, radii, shadows, screenshot frames — the entire visual design as tokens. No other file may hardcode design values.
docgen.config.json
Pipeline definition: sources, template version, and the kb section — API base path, body cap, and the controlled category vocabulary that must match the adopting product's server-side KB component list exactly.
templates/ + CLAUDE.md
The authoring contract: five page skeletons plus the rulebook both humans and AI assistants follow. Bump templateVersion only when these change — it deliberately marks every generated page stale.

Generation process — deterministic diff first, AI second

Two generation lanes share one rule: machines decide what changed, AI only writes inside a template, humans gate everything. Nothing is ever regenerated wholesale — the manifest remembers what exists and who touched it.

Lane A — API reference from the product's OpenAPI spec

The REVIEW guarantee: a page whose humanEdited flag is set is never overwritten by generation — a contract change on it is routed to a human instead. Hand-polish is permanent, not a casualty of the next build.

Lane B — user guides from the running product (the ui-guide recipe)

  1. Seed demo data in the product app — screenshots must never show customer data.
  2. npm run login — capture a Playwright storage state for authenticated pages.
  3. Media manifest — declare each screenshot/video: URL, selector highlights, output name.
  4. Write the guide pages from templates/task.md with the KB frontmatter trio (category · keywords · audience).
  5. Gates — vale, markdownlint, typecheck, tests, build.
  6. npm run docgen:kb-export — plan (dry-run), then --write to publish into the product KB.

Coverage tracking: docs/framework/kb-coverage.md — which product modules have guides, and the writing order (support volume first).

Manual edits — change a page, keep every artifact honest

Editing is plain markdown; the framework's job is making sure a manual edit can't silently rot the site, the PDF, the manifest, or the AI corpus.

The edit loop

  1. Branch from main; open the page under docs/ (or start from a template for a new one).
  2. npm run start — live reload; see the change as you type.
  3. If the change needs a screenshot: update the media manifest and re-run npm run capture — assets regenerate pixel-consistent, no image editor involved.
  4. Run the gates (lint:md · lint:prose · typecheck · test · build).
  5. PR → CI re-runs the same gates → review → merge.
  6. Re-export downstream: rebuild site/PDF; run docgen:kb-export so the AI corpus picks up the change (only the changed pages upsert — hash-diffed).

What protects a manual edit

provenance
humanEdited flag. Editing a generated API page flips it to human-owned in docgen/manifest.json; every future contract change on it becomes a REVIEW plan item — generation will never overwrite your wording.
idempotent export
Hash-diffed KB sync. The KB manifest stores a content hash per page; re-running the export upserts only pages whose exported payload actually changed. A whitespace-only merge touches nothing downstream.
style guard
Vale + markdownlint as reviewers. Banned filler words, heading structure, broken links — a malformed edit cannot merge, whoever (or whatever) wrote it.
honesty rule
Text must stand alone. Steps may never say "as shown below" with the meaning only in an image — alt text and step text carry the full instruction, because the AI and the PDF both read text.

Images & videos — scripted, named, and text-backed

Media is treated as generated code, not attachments: every asset is reproducible from a command + manifest, lives at a predictable path, and carries text (alt/caption) that survives into every text-only consumer.

Storage layout

static/
  img/<section>/<verb-object>.png     e.g. static/img/items/add-item-2.png
  video/<section>/<flow-name>.mp4     webm master → web-ready mp4 (+ poster jpg)
tools/
  flows/<flow>.mjs                    scripted Playwright journeys (login, add-item…)
  media manifests                     what to shoot: URL, selectors to highlight, output

Naming = the page's verb-object slug, so a page and its assets sort together. Tests (media-manifests.test.mjs) keep manifests well-formed and single-frame consistent.

Capture pipeline

Rules that make media safe

never
Real customer data on screen — seeded demo data only, enforced by the recipe.
always
Real alt text describing exactly what's shown — it is the image's representative in the PDF and the AI corpus.
refresh
UI changed? Re-run the capture commands — assets regenerate identically framed; no manual screenshotting drift.

Upstream & downstream — what feeds this repo, and what it feeds

DocsGen sits between the product (upstream truth) and every surface where its words reach people or models (downstream). Each edge is versioned and diffable.

Why the edges stay honest

Upstream drift is detected, not assumed. API changes surface as plan items (hash diff); UI changes surface as stale screenshots regenerated by command; vocabulary drift fails the KB export validation loudly.
Downstream is pull-only and versioned. Consumers never edit the corpus in place: the site and PDF rebuild from main; the KB upsert is slug-keyed with server-side version history; the AI reads the KB read-only at answer time.
One writing effort, compounding returns. A single well-written task page simultaneously improves the help center, the PDF, ticket deflection, and every future AI answer that grounds on it.
Product-agnostic by design. Everything product-specific lives in site.config.ts + docgen.config.json + .env — point the framework at any product with npm run init-product.
